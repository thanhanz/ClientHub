# Minimal Runner design — HF-002-R1

Status: PROPOSED / OWNER REVIEW REQUIRED. No execution authorization, approved task, checkpoint, or milestone acceptance is created by this document. Companion documents: [contracts](proposed-contracts.md), [task breakdown](proposed-task-breakdown.md), [review and prerequisites](review.md).

## Authority and proposed choices

Existing requirements come from [execution policy](../../policies/execution.md), [roadmap](../../README.md), [goal](goal.md), and AGENTS.md: one fresh session per bounded task; Runner-owned independent checks/evidence; approval and revision binding; scope enforcement; atomic checkpoints; bounded execution; no advancement across an unapproved milestone. The choices below implement those requirements only if approved. Existing checklist boxes remain unchanged.

Propose one local PowerShell 7 CLI, `scripts/harness/runner.ps1`, using Git, .NET filesystem/process APIs, and JSON. No daemon, database, scheduler, service, package framework, automatic commits, or product features. JSON validation is an explicit strict validator for the small v1 contracts rather than an added schema library. Pester is not required; a plain PowerShell test driver throws on failed assertions and returns nonzero.

The CLI accepts one run ID, one approved milestone, an approval record, a specification manifest, and `start`, `resume`, or `cancel`. It loads a finite approved task set, chooses one ready task in stable ID order, and launches a separate `codex exec` process for that task. No shared conversation or resume-session ID. Before implementation, owner must approve this mechanism and the installed CLI's supported arguments, structured output collection, permission isolation, process-tree cancellation, and authentication. If capability probing fails, stop; do not silently substitute an interactive or history-sharing adapter.

Use an isolated Git worktree per run, rooted at the approved clean commit. Keep generated records in the original workspace's ignored `harness/runs/<run-id>/`; never copy unrelated work into the execution tree. Run state and verification inputs are outside the coding agent's writable scope. Agent permissions must deny access to the original workspace and Runner evidence; prompts alone are insufficient. Runner configuration and verifier come from the approved clean baseline, not agent-modified scripts. No agent commits are accepted: HEAD/index changes stop the attempt.

## Approval, readiness, and bootstrap

Approval must name milestone 002, approver/date, a SHA-256 manifest digest, exact approved tasks and gate digests, scope, and limits. Manifest covers goal, policy, router, resolved design/contracts, task bytes, checks and prerequisite specifications. Canonical revision is the digest of a sorted UTF-8 JSON manifest with fixed key order, slash paths and SHA-256 file bytes; the human label HF-002-R1 alone is insufficient. Approval/acceptance records are read-only inputs, not Runner assertions. Any mismatch stops before dispatch; revised gates need renewed approval.

001 acceptance must be explicit and bound to its actual revision and reviewed evidence. A checked box, roadmap direction, or candidate manifest is not acceptance. For bootstrap tasks, an external operator supplies independent verification evidence (commands, exits, tested tree, reviewer/date and dependency mapping); no invented Runner checkpoint is required. After Runner availability, only its committed verification records qualify. Cycles, missing tasks/contracts, wrong milestone, missing checks or missing dependencies fail closed. All dependency evidence must still match the approved revision and code ancestry/content requirements in the contracts.

002 implementation remains one explicitly assigned task per fresh manually started session until independent dispatch exists. No task auto-creates its successor's approval. Task documents under `tasks/` may be issued only after approval; this proposed breakdown lives outside that directory.

## Scope and exact tested tree

Validate relative literal file paths or directory prefixes with segment boundaries; reject absolute paths, `..`, drive/UNC paths, alternate data streams, case aliases, symlinks/junctions/reparse points and paths resolving outside the worktree. Match Windows paths case-insensitively, preserving canonical spelling. Never allow `.git`, Runner evidence, approval inputs or protected verifier to be written. Check both sides of renames and deletions, tracked/staged/unstaged and untracked files. An out-of-scope edit stops verification and is preserved for review, never auto-deleted.

Capture a complete input inventory before dispatch. Inventory hashes relative path, raw bytes, file kind/mode, HEAD and index; include tracked and untracked files, including ignored files except narrowly enumerated Runner-owned output directories. Reject ignored source/config files and unexpected generated files; do not use broad Git-ignore filtering as a scope exemption. Allow only declared build-output roots, clean them before gates, and reject links within them. Generated output cannot be task input. A manifest digest identifies exact tested source bytes, including pending edits; a commit ID alone does not.

After agent exit, Runner checks scope and handoff consistency, snapshots the candidate, runs its own approved gate argv in the candidate worktree, records exits and assertions, then inventories again. Any source/index/HEAD mutation during or after gates invalidates results. Gates that legitimately write outputs must declare output roots; source-changing formatters cannot be acceptance gates. Unexpected files or missing output/assertions fail. Before checkpoint publication and every resume/next-task dispatch, recheck approval, dependencies and tree. Preserve old evidence as historical but mark it invalid for reuse when bytes, approval, task, command, environment identity or prerequisite evidence changes. Invalidate affected task and transitive dependents; stop for reconciliation rather than downgrade silently and execute.

Verified cumulative code advances only by a durable content snapshot/manifest stored by the Runner; restore snapshots solely into an empty disposable worktree after approval and integrity checks. No reset, checkout or merge over user changes. Dependency readiness requires evidence for the current cumulative source manifest (or explicit independent regression verification on that manifest), not merely an older task's PASS. Run all previously required gates on the current tree before granting cumulative readiness. Earlier product regression gates are included only when approved/applicable; a harness self-test does not establish product acceptance.

## Exclusive execution and checkpoint protocol

Acquire an OS-held exclusive file handle on a workspace lock keyed by canonical repository/common Git directory, covering all run IDs and worktrees. Hold through dispatch, checks and publication. A second writer exits before changing anything. Lock metadata includes PID/start time/run ID for diagnosis; stale metadata is not authority to steal a live lock. OS lock release after process death allows recovery, but a surviving child must be terminated/reconciled before reuse. Cancellation signaling is a narrow external control operation, not a second state writer.

Write immutable attempt start and completion evidence with monotonically increasing IDs. Persist JSON through same-volume temporary files, flush to disk, then atomic replace/rename. Publish a checkpoint bundle (manifest, gates, evidence hashes) durably first; replace `state.json` last with its reference and generation. State is the sole commit marker. A crash before replacement leaves an orphan, never VERIFIED. A crash after replacement requires hash/generation validation on resume. Corrupt/truncated/missing evidence stops; do not guess the last successful task. Fault-injection tests cover every publication boundary. Power loss durability is limited by Windows/filesystem guarantees; support local NTFS only for v1 and fail capability checks elsewhere.

State transitions: READY -> RUNNING -> VERIFYING -> READY (valid checkpoint), or STOPPED_FAILED / STOPPED_SCOPE / INTERRUPTED / CANCELLED / BLOCKED. Once all approved tasks are independently checked, transition to AWAITING_OWNER_REVIEW and exit. This is not milestone acceptance. No dispatch of 003, even if task files exist.

## Interruption, dirt, retry and cancellation

Default proposal: at most two attempts total per task across restarts, 30 minutes agent time, 10 minutes per gate, 60 minutes total per task including verification, 10 seconds graceful termination then process-tree kill. No automatic retries for scope, stale approval, ambiguity, corrupt state, missing prerequisite or cancellation. One retry for ordinary gate/process failure only after an explicit operator reconciliation decision; it consumes the persisted budget and uses a fresh session. Deadlines use monotonic elapsed time while running plus persisted conservative consumed time; clock rollback/restart never resets budget.

Ctrl+C or `cancel` signals the supervisor, stops dispatch, terminates agent/check descendants, records partial evidence and exits nonzero. Use a Windows Job Object with kill-on-close, assigned before child execution, so Runner death cannot leave a writer running. If this cannot be guaranteed with the selected CLI, implementation is blocked. Cancellation is never PASS; resume requires explicit operator intent and remaining budget.

Original dirty workspace: report inventory/status, do not stash, clean, reset, commit or copy dirt. Default start blocks until operator supplies a clean committed baseline or authorizes an isolated worktree from an explicit approved commit with unrelated dirt excluded. Current untracked 003 draft is unrelated and must remain untouched. Execution-worktree dirt after failure/interruption is frozen with evidence. Operator can preserve it and create a clean retry worktree, or explicitly adopt reviewed in-scope edits as a new attempt baseline; adoption never makes them verified. Outside-scope/unknown edits block until disposition is recorded. Resume recomputes inventory and validates locks, child termination, approval and checkpoints before selecting anything.

## Verification boundary

Tests use temporary synthetic Git repositories, fake session processes and trusted deterministic gates; no real model, product sources, credentials or expected scenario answers in agent bundles. A real CLI smoke test demonstrates fresh invocation, isolation and cancellation separately. Test driver checks dispatch count, exact state/evidence, actual exit codes and absence of unauthorized checkpoint/next-task launch. [Task breakdown](proposed-task-breakdown.md) assigns the full failure matrix. Bootstrap verifier is run by an independent operator against a captured tested tree; agent-reported tests are handoff claims only.
